# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Workflow

- Commit every change (even small fixes) with `git commit` — don't leave edits uncommitted at the end of a turn.
- After any change that affects app code, rebuild and reinstall on the connected phone so it can be tried immediately:
  `.\gradlew.bat installDebug` (falls back to `& "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe" devices` to confirm a device is attached if `adb` isn't on `PATH`).

## Project

Diafit is an Android app (Kotlin, Jetpack Compose) for people with diabetes. It aggregates CGM, nutrition, activity, and sleep data from remote sources (Nightscout, Tidepool, Google Health Connect) and local sources (xDrip, AndroidAPS/AAPS, Juggluco), and applies visual analytics / AI to support glucose management.

- Package namespace: `uk.scimone.diafit`
- `minSdk` 28, `targetSdk` 36, `compileSdk` 37, JVM target 11 (toolchain upgraded 2026-10-06, see Charts section)
- `app/build.gradle.kts`'s `BASE_URL`/`API_KEY` `buildConfigField`s are only the **first-run defaults** (2026-10-06) — the Nightscout base URL and API secret are now user-configurable in Settings (`NightscoutConfig`, `GetNightscoutConfigUseCase`/`SetNightscoutConfigUseCase`), read at request time by `NightscoutApi`/`constructUrl`. There's also an OpenAI-compatible base URL + API key setting (`AiConfig`), defaulting to `https://api.openai.com/v1`, used for meal-photo nutrient analysis (see below). Both are plain `SharedPreferences` via `SettingsRepositoryImpl`, not encrypted — don't treat them as secret storage.

## Architecture

Clean Architecture + MVVM, organized as **feature packages** under `app/src/main/java/uk/scimone/diafit/`, each typically split into `di/`, `presentation/` (Compose screens + ViewModels), `domain/` (use cases, models, repository interfaces), and `data/` (repository impls, local/remote sources):

- `core/` — shared infrastructure used by every feature: Room database (`core/data/local`), Ktor networking to Nightscout (`core/data/networking`), repository interfaces/impls for CGM/Bolus/Meal (`core/domain/repository`, `core/data/repository`), shared use cases, and the health-sync-source abstraction (see below).
- `home/`, `journal/`, `addmeal/`, `settings/` — individual feature modules, each wired up via its own Koin module in `<feature>/di/`.
- `ui/` — Compose theme.
- `debugintent/` — manual debug entry point for simulating external intents.

There is no navigation library: `MainActivity` holds a single `selectedTab` int and switches between feature screens (`HomeScreen`, `JournalScreen`, `SettingsScreen`, `AddMealScreen`) in a `when` block, with `BottomNavigationBar` driving tab selection. `userId` is currently hardcoded to `1` in `MainActivity` (no auth system yet).

### Dependency injection (Koin)

All DI modules are registered in `DiafitApp.onCreate()` via `startKoin { modules(...) }`. Feature ViewModels that need per-instance params (e.g. `userId`) are registered with `viewModel { (userId: Int) -> ... }` and resolved with `koinViewModel { parametersOf(userId) }` at the call site.

### Sync source abstraction

External data sources (Nightscout, xDrip, Juggluco, AAPS) implement `HealthSyncSource` (`core/domain/repository/syncsource/HealthSyncSource.kt`), with `IntentHealthSyncSource` for sources that receive data via broadcast `Intent` (xDrip, Juggluco, AAPS) rather than polling. Implementations live under `core/data/repository/syncsource/{cgmsyncsource,bolussyncsource}/`.

Sources are bound in `core/di/syncModule.kt` using **named Koin qualifiers** (`named("NIGHTSCOUT")`, `named("XDRIP")`, `named("JUGGLUCO")`, `named("AAPS")`), then collected into a `sources: Map<CgmSource/BolusSource, HealthSyncSource>` passed to `SyncCgmDataUseCase` / `SyncBolusDataUseCase`. The active source is a user setting (`settings/domain/model/CgmSource`, `BolusSource`) read via `GetCgmSourceUseCase`/`GetBolusSourceUseCase`, and chosen by the user on the Settings tab.

CGM sync runs as a foreground service (`core/data/service/CgmServiceManager` + `RemoteCgmSyncService`) started from `MainActivity.onCreate()` and restarted whenever the user changes CGM source (`SettingsViewModel.restartCgmServiceEvent`). Broadcast-based sources are handled by the manifest-declared `HealthReceiver` (`core/presentation/receivers`, works regardless of whether any service is running) enqueuing `BolusBroadcastWorker`/`CgmBroadcastWorker` (WorkManager, now requesting expedited execution). **Important:** those workers only parse the broadcast if it matches the user's *currently selected* Settings source (`CgmBroadcastWorker.kt`/`BolusBroadcastWorker.kt` call `GetCgmSourceUseCase`/`GetBolusSourceUseCase` and `when` on it) — a broadcast from xDrip/Juggluco is silently dropped (logged, not inserted) if the user hasn't selected that source in Settings, even though the receiver still "received" it.

**Overnight background reliability (added 2026-10-05):** the test device (Xiaomi, Android 16) stopped receiving CGM values after being left idle overnight — most likely the OS/OEM killing the foreground sync service or deferring WorkManager jobs during Doze, since MIUI/HyperOS is known for aggressive background app killing even beyond stock Android's battery optimization. Mitigations in place: `RemoteCgmSyncService`/`BroadcastIntentHealthSyncService` return `START_STICKY`; `CgmServiceManager.start()` is idempotent and gained `ensureRunning()`, which checks whether the CGM sync notification (`CgmServiceManager.CGM_SYNC_NOTIFICATION_ID`) is still active and force-restarts only if it isn't; a new periodic `CgmServiceWatchdogWorker` (registered in `DiafitApp.onCreate()`, minimum WorkManager interval of 15 min) calls `ensureRunning()` for whatever source is currently selected, which self-heals even after a full process death since WorkManager persists across that. None of this can fully override OEM-specific background-kill policies — the Settings screen's "Background reliability" section links straight to MIUI/HyperOS's Autostart management activity on Xiaomi devices (`com.miui.securitycenter`/`com.miui.permcenter.autostart.AutoStartManagementActivity`, via an unofficial but widely-used component name — wrapped in try/catch since it isn't guaranteed stable across MIUI/HyperOS versions), since enabling Autostart is a user-granted permission no code change can substitute for. Not yet verified whether these mitigations actually survive a full overnight test — reconfirm with the user after a night's use.

**Known gotcha (confirmed on-device 2026-10-05):** Juggluco's "Data exchange" settings has independent toggles for several broadcast formats ("XDrip broadcast", "Glucodata broadcast", "Patched Libre", "LibreView", "Eversense") and can fire more than one concurrently, on independent per-minute cadences. If xDrip+ (`com.eveningoutpost.dexdrip`) is *also* installed and receiving Juggluco's "XDrip broadcast" output, it will separately re-broadcast as `com.eveningoutpost.dexdrip.BgEstimate` (with `SourceDesc: Other App` in the extras — that's the tell it's a relay, not Juggluco talking directly). Don't assume which format is "the" Juggluco broadcast from one sample; a short (<2 min) logcat capture can plausibly miss the `glucodata.Minute` tick entirely and show only the xDrip-relayed one, which looks identical to a real mismatch. Capture at least 2–3 minutes (`adb logcat "HealthReceiver:D" "CgmSync*:D" "CgmInsertWorker:D" "*:S"`) before concluding a source is wrong. In practice: selecting "JUGGLUCO" in Settings correctly parses Juggluco's native `glucodata.Minute` broadcast with no xDrip+ dependency — confirmed with consecutive successful inserts one minute apart. **Setup step required in Juggluco itself:** its "Glucodata broadcast" toggle isn't a single global on/off switch — Juggluco → Settings → Data exchange → Glucodata broadcast opens a per-app allow-list of installed apps; `uk.scimone.diafit` (Diafit) must be individually switched on in that list, or the broadcast never reaches Diafit even though Juggluco's own UI shows readings updating every minute. A more robust fix would have `CgmBroadcastWorker` dispatch by the intent's actual `action` (each `IntentHealthSyncSource` already exposes its own `ACTION` constant) instead of gating on the Settings selection at all, so a stray broadcast from an unselected/relaying source is cleanly ignored rather than logged as a confusing "unexpected action"; not done yet.

### Networking

Ktor client built via `core/data/networking/util/HttpClientFactory`; Nightscout REST calls live in `core/data/networking/NightscoutApi.kt` with DTOs in `networking/dto/`. Results use a custom `Result`/`NetworkError` sealed-type wrapper (`core/domain/util/networking/`) rather than exceptions — `safeCall`/`responseToResult` convert Ktor responses into this type.

`core/data/networking/OpenAiApi.kt` is a second Ktor client (same `HttpClient`/`HttpClientFactory` instance) for the OpenAI-compatible `/chat/completions` vision endpoint, used by `MealAnalysisRepositoryImpl` to turn a meal photo into estimated nutrients. The request body is built as a raw `JsonObject` (not a `@Serializable` request DTO — the OpenAI `content` array mixes a text part and an `image_url` part, which doesn't map cleanly onto kotlinx.serialization's polymorphism without a custom serializer); the response is a typed `ChatCompletionResponseDto`, but its `choices[0].message.content` is itself a JSON *string* (the model's answer) that gets parsed a second time, defensively, by hand-walking a `JsonObject`/`JsonArray` tree in `MealAnalysisRepositoryImpl.parseAnalysis` — numeric macronutrient fields are read via `JsonPrimitive.content` + `toDoubleOrNull()` rather than strict typed deserialization, since the model may return them as either JSON numbers or strings depending on prompt adherence. Triggered from `AddMealViewModel.analyzeMeal()` via an explicit "Analyze with AI" button in `AddMealScreen` (not automatic on photo capture, so a misconfigured/missing API key never blocks the manual-entry flow) — populates carbs/protein/fat/calories/impact-type/description but leaves every field editable before save. `CreateMealUseCase`/`MealEntity.reasoning` is filled from the analysis; `MealEntity.recommendation` is intentionally left `null` — the model prompt only asks for a nutrition breakdown, not an insulin dosing recommendation (see §7.5 in `project_concept.md`, still unimplemented).

### Charts

Glucose/activity visualizations use **Vico** (`com.patrykandpatrick.vico`, Compose + M3 theming), under `home/presentation/components/`. Insulin activity-curve math lives in `core/domain/model/InsulinActivity.kt`.

**Vico 3.3.1** (upgraded 2026-10-06 together with the whole toolchain: AGP 9.4.1, Gradle 9.8.0, Kotlin 2.4.10, KSP 2.3.12 replacing kapt for Room, `compileSdk` 37 / `targetSdk` 36, Compose BOM 2026.09.00, Ktor 3.6, Koin 4.2, Coil 3 (`io.coil-kt.coil3`, package `coil3.compose`), Room 2.8.5). Vico 3 folded `core` into the single `compose-m3` artifact and moved everything to `com.patrykandpatrick.vico.compose.*`; API differences hit during migration: `rememberStartAxis`/`rememberBottomAxis` → `VerticalAxis.rememberStart`/`HorizontalAxis.rememberBottom`; `AxisValueOverrider` → `CartesianLayerRangeProvider.fixed`; `HorizontalLayout`/`horizontalLayout` → `layerPadding`; `BaseAxis.SizeConstraint` → `BaseAxis.Size.Fixed(dp)`; components/`Fill`/`Shape` are now Compose-native (`rememberLineComponent`, `rememberShapeComponent`, `CircleShape`); `CartesianChartModelProducer.build()` → `CartesianChartModelProducer()`; `Zoom.static` → `Zoom.fixed`; `Defaults` is internal (hardcode `10f` max zoom); `VerticalAxis.ItemPlacer` margins renamed `getTopLayerMargin`/`getBottomLayerMargin`. AGP 9 has built-in Kotlin, so the `kotlin-android` plugin is gone (only `kotlin-compose`/`kotlin-serialization` remain) and kapt is replaced by `ksp`.

**Shared time axis (all four Home charts)** — the helpers live in `TimeAxisUtils.kt`. For stacked charts sharing one `VicoScrollState`/`VicoZoomState` to line up pixel-for-pixel, all of these must match across charts: (1) start-axis width (`SharedStartAxisSize`, fixed 36.dp); (2) content-independent zoom bounds (`Zoom.fixed`, never the `Zoom.Content` default); (3) the layer's **x-spacing** — Vico derives pixels-per-x-step from each layer (`LineCartesianLayer`: point size + `pointSpacing`; `ColumnCartesianLayer`: column width + `columnCollectionSpacing`), so `ChartXSpacing` (38.dp) is split into `ChartPointSpacing`/`ChartColumnSpacing`; without this the column chart ran at a different zoom than the line charts; (4) layer end-padding: line layers pad by half the point marker (*unscalable*), column layers by half the column (*scalable*, multiplied by zoom), so each chart type gets the other's padding via `layerPadding` (`LineChartLayerPadding` / `ColumnChartLayerPadding`). The x axis ends `TIME_AXIS_FUTURE_HOURS` (2h) past now (`timeAxisMaxX`) so data never touches the right edge; `getTimeAxisBounds` floors "now" to the minute so each chart computes the same bounds. Verified via `adb shell screencap` with identical gridline x positions on all charts (column-chart *bars* themselves not yet verified against real bolus/carb data — recheck when there is some).

**Home chart layout & zoom (2026-10-06):** three compact stacked panels sharing one x axis — CGM, insulin, carbs — and only the last (carbs) draws the hour labels (`showTimeLabels`). The insulin and carb panels are the same generic `ComponentEventActivityChart`: the summed activity curve as a filled area (extended 2h into the future; y labels hidden, shape only — insulin via `InsulinActivity`, carbs via `CarbActivity`, a Beta(2,3) absorption curve over the meal's `impactType.durationMinutes`) plus each event as a **bubble sitting on the zero line**, area ∝ value, labelled "6.8 U" / "45 g". Bubbles are a second `LineCartesianLayer` on the axis-less end axis (fixed 0..1 range, y=0); Vico's point provider/data label only see `y`, so the value is encoded as a negligible offset (`value * 1e-4`) and decoded in `EventBubbleProvider`/the label formatter; `BottomAnchoredCircle` draws the circle *above* the point (Vico centres points on y) and the reported point size is 2x the drawn diameter so the label clears the bubble. `getLargestPoint` is deliberately constant — Vico pads layers by half the largest point and any variation breaks the x alignment.

**Alignment checklist beyond the above (all learned the hard way, verify by screenshot):** (a) *one* `nowMinute` computed in `HomeScreen` and passed to every chart (`getTimeAxisBounds(nowMinute)`) — charts recompose at different times (CGM with each reading), so a per-chart "now" drifts apart; (b) the same tick component on every bottom axis (its thickness feeds the layer margin) — hidden-label charts use `tickLength = 0.dp`, not `tick = null`; (c) `addExtremeLabelPadding = false` on the shared item placer. Default zoom shows the last 6h + 2h future (`Zoom.x(visibleHoursMillis(6))`); zoom chips (3h/6h/12h/24h, `ChartZoomControls`) call `animateZoom` + `animateScroll(End)`; pinch works within 3h..26h. **Gotcha:** the `Zoom` objects passed to `rememberVicoZoomState` must be `remember`ed — it's a `rememberSaveable` keyed on them, so fresh lambdas every recomposition (HomeScreen recomposes every second) silently reset the user's zoom.

**Carb ingestion (2026-10-06):** `HealthReceiver` enqueues `CarbBroadcastWorker` for `CARBS_ACTIONS` (same `info.nightscout.client.NEW_FOOD` action as AAPS boluses; the action name looks odd for treatments but it's what the bolus path already uses). `AapsCarbParser` reads the `carbs` field of every entry in the `treatments` JSON array and inserts photo-less `MealEntity`s (`imageId = ""`, `description = "Carbs (AAPS)"`, impact MEDIUM), deduped by `sourceId` (`MealRepository.existsBySourceId`); gated on the selected bolus source being AAPS. **Unverified against a real AAPS install** — tested only with fake broadcasts: `adb shell am broadcast -a info.nightscout.client.NEW_FOOD -n uk.scimone.diafit/.core.presentation.receivers.HealthReceiver --es treatments '[{"_id":"x","date":<epoch ms>,"carbs":45}]'` (delete test rows afterwards: pull the db with `run-as`, edit with python `sqlite3`, push back with the `-wal`/`-shm` removed). The Home meal-photo row only shows meals that have a photo.

### UI

`BottomNavigationBar` (`core/presentation`) uses Material3 `NavigationBar` with filled/outlined icon pairs per tab (`material-icons-extended` dependency) plus a custom raised circular button for the Add-meal action. Tabs (2026-10-06): Home, Summary (stub), Journal, History (see below) — `ADD_MEAL_TAB_INDEX = 5` for the FAB. Settings is **not** a bottom tab; it's reached via `SETTINGS_TAB_INDEX = 4`, opened from an overflow (⋮) menu in `MainActivity`'s top `TopAppBar` (`@OptIn(ExperimentalMaterial3Api::class)` on `onCreate`), matching the original wireframe in `project_concept.md` §9. **Gotcha:** don't put `fillMaxHeight()` on a custom child inside `NavigationBar`'s row — Material3's `NavigationBar` only sets a *minimum* row height (not a max/fixed one via `defaultMinSize`), and `Scaffold` gives the `bottomBar` slot loose/tall height constraints so custom bars can be as tall as needed; a `fillMaxHeight()` child makes the whole bar balloon to nearly fill the screen, squeezing all page content into near-zero height. Use `Modifier.align(Alignment.CenterVertically)` (a `RowScope` extension) instead to vertically center a custom item without affecting the row's height. This exact bug shipped once during development (2026-10-05) and was caught by rendering the app and screenshotting via `adb shell screencap` — always do that after a bottom-bar/Scaffold layout change rather than trusting it compiles.

`SettingsScreen` is organized into `SettingsSection` cards (icon + title + content), each holding a logical group (CGM source, Bolus source, glucose target range, background reliability).

### Persistence

Room database `AppDatabase` (`core/data/local/AppDatabase.kt`) with DAOs for CGM, Bolus, and Meal entities. Schema exports go to `app/schemas` (`room.schemaLocation` ksp arg); migrations are added explicitly (e.g. `MIGRATION_9_10`) in `coreModule.kt` — bump and add a migration when changing any `@Entity`.

### Journal & meal editor (redesigned 2026-10-06)

`JournalScreen` is a day-grouped list (sticky `DayHeader` with per-day summary) of `JournalEntryCard`s. Entries are generic: `JournalEntryUi` (sealed; only `MealEntityUi` exists) + `JournalEntryKind` (MEAL / SLEEP / ACTIVITY, the latter two `available = false`) in `journal/presentation/model/EntryVisuals.kt`, which also holds the icon/label/accent mappings for `MealType` and `ImpactType` (shown to users as **Fast/Medium/Slow absorption**; enum names SHORT/MEDIUM/LONG stay since they're persisted). To add a kind: new entity + `JournalEntryUi` subtype, a card branch in `JournalEntryCard`, a detail screen and editor, an `Overlay` case in `MainActivity`, then flip `available`. The filter-chip row appears automatically once more than one kind is available.

There is still no nav library: `MainActivity` keeps an `overlays` stack (`Overlay.MealDetail` / `Overlay.MealEditor(mealId?)`) of full-screen pages drawn above the tabs; the + button opens `NewEntrySheet` (kind chooser) instead of switching tab. Delete is a **soft delete** (`MealEntity.isValid = false`, `SetMealValidUseCase`) with an Undo snackbar hosted in `MainActivity`; every meal query used by the UI filters `isValid = 1`, but the import-dedupe queries (`countBySourceId`/`countImportedAt`) deliberately don't, so a deleted AAPS carb entry isn't re-imported. `MealDetailScreen` shows the photo, a glucose-response chart (`GlucoseResponseChart`, a plain Canvas, not Vico; data from `GetGlucoseResponseUseCase`: CGM 45 min before to 1 h after the absorption window, plus boluses; mg/dL only), stats, nutrition, absorption and AI notes. `MealEditorScreen` (was `AddMealScreen`) is shared by create and edit (`AddMealViewModel.startNewMeal()` / `startEditing(id)`); the photo is optional (`CreateMealUseCase` takes a nullable `imageUri`, `imageId = ""` when none); meal type and absorption are auto-suggested (from time / macros) until the user picks one (`mealTypeAuto`/`impactAuto`); replacing a photo uses a fresh `imageId` and the old file is deleted on save (`UpdateMealUseCase`). Icons: `ic_meal_type_*` (sunrise / sun / moon / apple) and `ic_absorption_*` (curve glyphs) are 24dp stroke vectors. Not yet done: swipe-to-delete in the list, mmol/L in the chart, saving an edit doesn't re-run AI analysis.

**Journal time filter & compact meal cards (2026-10-06):** `JournalRange` is the last 30 days (`DEFAULT_RANGE_DAYS`) unless the user picked a custom first–last day: no presets, the `RangeChip` opens a `DateRangePicker` directly and shows a ✕ to go back to the default. It lives in `JournalViewModel` (`setRange`); meals are filtered before outcomes are computed, lows/highs are searched within the range (capped at 180 days back). The chip sits first in a horizontally scrollable row with the kind filter chips. `MealCard` is a single ~96 dp-high row: clean 96 dp photo (+N badge), a middle column (heading line "time · type · courses" with the absorption badge right next to the type, one-line title, glucose outcome box "87 → peak 116 after 1h 6min" + range bar + %), and the at-a-glance numbers on the right like the lowest value of a low card (carbs "12 g" yellow, insulin "7.8 U" blue, `BigValue`). The AAPS source label is intentionally not shown on the card, and the heading line is uncoloured. The right column has a fixed width (`MEAL_VALUES_WIDTH`) and the % text a fixed width so the outcome box/range bar is identical on every card; glucose timing is written compactly ("· 1h 6m"). **Standalone boluses:** boluses outside every meal's dose window (`List<BolusEntity>.standalone(sittings)` in `core/domain/model/StandaloneBolus.kt`) appear as `BolusEntryUi` / `BolusCard` entries (kind `JournalEntryKind.BOLUS`, not creatable, not clickable) in the Journal and in the History day page's Journal tab; SMBs are included too, but summed into one entry per local clock hour (`toBolusEntries`, `BolusEntryUi.isSmb/count`, shown as "10:00–11:00 · Automatic · 6 SMBs"; unit-tested in `BolusEntryTest`, not yet seen on-device since the DB had no standalone SMBs). Units (g, U, mg/dL) on all cards are coloured like their value. The Journal day header counts them ("1 bolus"). **Gotcha:** `JournalViewModel`'s `range` property must be declared before the `init` block that calls `observeEntries()` (it crashed with an NPE once because of declaration order).

### Journal cards (2026-10-06)

### Meal editor layout (redesigned 2026-10-07)

`MealEditorScreen` layout: the **top bar title is the entry's name**, typed in place (`TitleField`: small overline "New meal / Add course / Edit … · named by AI" over a borderless field; replaces the old "What did you eat?" card). Directly under it a compact `WhenRow` of pills (date and time opening M3 `DatePickerDialog`/`TimePicker` dialogs, meal type as a dropdown; hidden for courses). ### Multi-photo courses & extended meals (2026-10-06)

Concept: a **meal** (what the user thinks of: "sushi dinner") is made of one or more **courses** (what arrived at one moment: a plate, a dessert). Each course is a `MealEntity` row with its own time, macros and absorption, so the carb-activity curve of a long meal is the sum of staggered per-course curves rather than one lump at the start. Courses of one meal share `MealEntity.sittingId` (UUID; every meal created in-app gets one; imported AAPS carbs and pre-v11 meals have `null`). Grouping lives in `core/domain/model/MealSitting.kt` (`groupIntoSittings`/`toSittings`, unit-tested in `MealSittingTest`): same sittingId = one meal; two different sittingIds never merge; untagged entries join whatever they're within 15 min of (the old chaining behaviour). Used by Home (`groupMeals`), Journal (one card per meal, summed via `MealSitting.toUi`) and the meal detail page.
- **Photos:** a course holds up to `MAX_PHOTOS_PER_COURSE` (8). `imageId` stays the *cover* photo (so every older single-photo code path still works), extra photos are in `extraImageIds` (JSON `List<String>` via `Converters`); `MealEntity.photoIds` gives all of them. `CreateMealUseCase`/`UpdateMealUseCase` take the full ordered `List<MealPhoto>`; update deletes files no longer referenced. Gallery uses the system photo picker (`PickMultipleVisualMedia`, no permission).
- **AI:** `analyzeMealPhotos(List<Uri>)` sends all of a course's photos in one request (prompt: count each food once even if photographed twice). Images are downscaled with `ImageDecoder` (EXIF-aware, HEIC ok) to 1280 px / JPEG 85 before base64. Schema gained `dishes: [{name, carbohydrates}]`; with >1 dish the split is prepended to `reasoning` as bullet lines.
- **Adding a course:** a meal is "in progress" for `SITTING_OPEN_WINDOW_MS` (90 min) after its latest logged course (`GetOpenSittingUseCase`); the + sheet then shows "Add a course to …" as its first option. Also reachable from the meal detail page and the Home meal sheet. `Overlay.MealEditor(mealId = null, addToMealId = x)` opens `MealEditorScreen` in course mode (`AddMealViewModel.startAddingCourse`): a banner shows carbs and insulin so far (boluses from 30 min before the first course), the carbs field becomes "Carbs in this course" + running meal total; the meal type is inherited and hidden. Adding to a legacy meal without sittingId assigns one on save (`ensureSittingId`).
- **Detail page** (`MealDetailScreen`) is meal-level: photo pager over all photos, "Courses & insulin" timeline interleaving courses and boluses (dose window first course −30 min .. last course +30 min) with running totals and g/U, glucose chart spanning first course → last absorption end with a marker per later course; multi-course meals are edited per course (tap a timeline row), delete removes all courses (`SetMealValidUseCase(List<Int>)`, Undo restores all).
- **Home insulin/carb panels:** bubbles still chain-merge within 15 min, so many small boluses during a long meal become one labelled bubble; when merging happened, a `TickProvider` layer draws a small dot on the curve for each individual event. Its `getLargestPoint` is constant (x alignment).
- DB is **v11** (`MIGRATION_10_11`: `sittingId` + index, `extraImageIds TEXT NOT NULL DEFAULT '[]'`). Verified on-device: migration, + sheet, add course, journal card, detail timeline, delete-whole-meal + undo. **Not yet verified on-device:** multi-photo AI analysis against a real endpoint, camera capture of several photos in a row.

### Merging AAPS carbs into logged meals (2026-10-06)

Photo → AI estimate → carbs typed into AAPS' bolus calculator comes back as a second, photo-less `MealEntity` (the AAPS import). `MealMatcher` (`core/domain/model`, unit-tested in `MealMatcherTest`) pairs them one-to-one: the imported entry must arrive from 15 min before to 90 min after the logged course and its carbs be within max(5 g, 20 %); **confident** (auto-merged) = within max(2 g, 10 %), −10..+60 min and unambiguous, otherwise only a *suggestion*. A multi-course sitting can also be matched as a whole (one dose for several courses; then the imported row is only hidden, courses keep their carbs). `MergeCarbEntriesUseCase` applies it: the imported row gets `mergedIntoId` (hidden by every meal query except the import-dedupe ones, so it isn't re-imported), the logged meal's `carbohydrates` become the **dosed** carbs, the old value goes to `estimatedCarbs`, `aapsLinked = true`. Runs after `CarbBroadcastWorker` inserts and after `CreateMealUseCase`/`UpdateMealUseCase` (either order of arrival works; looks back 3 days). Suggestions are computed in `JournalViewModel` and shown as a "Same meal? AAPS carbs 45 g at 12:41 · Separate / Merge" strip under the meal card; "Separate" and Unlink set `mergeDeclined` on the imported row so it is never matched again. The meal page shows "Matched with AAPS" with Unlink; cards show "AAPS ✓". DB is **v12** (`MIGRATION_11_12`). Not yet verified with a real AAPS broadcast, only fake ones.

### Connectors & data sources (2026-10-08, step 1 of the settings redesign)

Settings is now **Connectors** (any number of `Connector`s switched on: Nightscout, AAPS, xDrip+, Juggluco, Health Connect; `settings/domain/model/Connector.kt`) plus **Data sources** (one connector per `DataType`: CGM, FOOD, BOLUS, BASAL, HEART_RATE, STEPS, SLEEP, EXERCISE, or Off). `Connector.provides` = live data, `canBackfill` = history it can hand over (Nightscout: CGM/bolus/food/basal; Health Connect: CGM + activity; AAPS/xDrip/Juggluco: none). Stored in `SettingsRepositoryImpl` (`connectors_enabled`, `source_<type>`; legacy `cgm_source`/`bolus_source`/HC flag migrated once, `connectors_migrated`). Enabling a connector makes it the source of every type it provides that has none yet; disabling hands its types to another connected provider or none; an explicit Off stays. `getCgmSource()`/`getBolusSource()` are now nullable derived views (null = stop CGM service / ignore). Gates: `CgmBroadcastWorker`/`BolusBroadcastWorker` (selected source), `CarbBroadcastWorker` (FOOD==AAPS), `TempBasalBroadcastWorker` (BASAL==AAPS), `PumpEventBroadcastWorker` (AAPS connected), `HealthConnectSyncer.syncActivity` (per activity type), Home/Day `activityConnected` = `isActivityEnabled()` (any activity type selected). Deselecting only stops ingestion (and hides the activity panel when all four are off); stored rows stay. Health Connect's one permission dialog asks for activity + glucose + background together. **Nightscout auth fixed** (`NightscoutAuth.kt`): SHA-1 `api-secret` header, or `?token=` for access tokens; Settings has "Test connection" (`/api/v1/verifyauth`). Verified on-device (migration, rendering). **Settings UI (compact):** each data type is one collapsed row (accordion in `DataSourcesSection.kt`) with a checkbox per connected connector; tapping the ticked box switches the data Off (no Off row). Nightscout credentials collapse to a one-line summary once set up / tested OK; AAPS/xDrip/Juggluco hints sit behind "Setup tips".

**Backfill (step 2, 2026-10-08):** under each selected data type, "Fill in past data": pick a backfill-capable connected connector (`Connector.canBackfill`), a range (7/14/30/90 days or a custom date range) and press Fill in. `BackfillRunner` (core/data/backfill, singleton, app-scope coroutine, one job at a time, status `StateFlow<BackfillStatus>`) first computes the gaps (`missing`): continuous types (CGM >= 4 readings/h, heart rate >= 3/h, steps >= 1/h) count an hour as covered from the stored rows; every type also counts ranges an earlier backfill already fetched (`BackfillCoverageStore`, prefs, needed for sparse data like boluses/meals/workouts; the last hour is never recorded). Only gaps >= 1 h are fetched. Nightscout: CGM one day per request; treatments (`NightscoutApi.getTreatments`, `find[created_at]`, 7 days per request) mapped by `NightscoutTreatmentMapper` (unit-tested) to boluses (dedupe by timestamp), meals (same dedupe as the AAPS import, then `MergeCarbEntriesUseCase`) and temp basals (`PumpEventEntity`, `sourceId = ns-temp-basal-<_id>`, skipped when within 90 s of a live one, cancellations stored as duration 0). Health Connect: `HealthConnectSyncer.backfill` reads one day per call; **HC only shares data up to 30 days before the first grant unless `READ_HEALTH_DATA_HISTORY` is granted**, so the panel offers "Allow older data" for longer ranges (the permission is also part of the connect dialog). Verified on-device: gap preview ("7 of 14 days") and a Health Connect steps fill-in (added 0: HC had nothing more). **Not verified:** any Nightscout backfill (no instance connected on the dev phone), the custom range picker, the history permission dialog, long ranges. An app-scope coroutine isn't a foreground service, so a long backfill can stop if the app is killed (safe to rerun).

### Nightscout as a full connector (2026-10-08, step 3)

Nightscout now provides every treatment-based data type live and as backfill: `BOLUS`, `FOOD`, `BASAL` plus two new `DataType`s, `PROFILE` ("Profile & targets": Profile Switch, Temporary Target) and `DEVICE` ("Pump & sensor changes": Site / Sensor / Insulin / Battery change, notes...). AAPS provides both new types live too. `pumpEventDataType(eventType)` / `PumpEventEntity.dataType` (PumpEventEntity.kt) classifies a stored event (Profile Switch/Temporary Target -> PROFILE, `Temp Basal*` -> BASAL, rest -> DEVICE); `PumpEventBroadcastWorker` now keeps an AAPS event only if AAPS is the selected source for its type. Settings migration `connectors_migrated_profile_device` selects AAPS (else Nightscout) for PROFILE/DEVICE for existing users, so nothing they already received stops.
`core/data/nightscout/NightscoutTreatmentImporter` (shared by backfill and the live sync) fetches `/api/v1/treatments` once per range and stores what the requested types ask for, via `NightscoutTreatmentMapper` (`toBolus`/`toMeal`/`toTempBasal`/`toPumpEvent`). Events dedupe on `sourceId` (= Nightscout `_id`) **and** on type + time within 5 s, since the live AAPS copy can lack `_id`. PROFILE also pulls `/api/v1/profile.json` (`profileDocToSwitch`) as a *baseline* "Profile Switch" at 100 % only when no switch with a profile is known at or before the range start, so basal/ISF/carb ratio exist for time before the first real switch (the profile collection is also rewritten by AAPS, so it is never used when real switches exist). **Live sync:** `NightscoutSyncWorker` (periodic 15 min via `NightscoutSyncScheduler.schedulePeriodic()` from `MainActivity`, plus `syncNow()` on app open, on connecting Nightscout and on selecting it for a type) re-reads the last 2 days for each type selected as Nightscout. Glucose keeps its own poller. Backfill of PROFILE/DEVICE works like the other sparse types (coverage store). Unit-tested mapper parts (`NightscoutTreatmentMapperTest`); **not verified against a real Nightscout instance** (none connected on the dev phone), and the worker's 15 min cadence is WorkManager's minimum, so treatments lag the live AAPS broadcast.

**Device events: origin, merging, notes (2026-10-08):** every stored `PumpEventEntity.rawJson` carries `_diafitSource` ("AAPS" / "Nightscout", `PumpEventNormalizer`, stamped by `AapsEventParser` and `NightscoutTreatmentMapper`); the Journal dialog says "Imported from <source>". `PumpEventRepair.runOnce()` (MainActivity, once per install) stamped older rows (imported > 30 min after the event = Nightscout, else AAPS). AAPS also logs a profile change as a **Note** (notes = "Anna" / "Anna (90%)", carrying `profileJson` with the percentage already applied): `profileNoteToSwitch` turns it into a Profile Switch (percentage from the name, duration 0, profile scaled back to the saved one) at import and in the repair; `isSameEvent` dedupes it against a real switch of the same profile within 2 min (other types: within 5 s). Hidden (soft-deleted) rows are not seen by the dedupe, so a deleted AAPS switch is replaced by its note. Journal: a Site Change + Insulin Change within 2 min is one card "Site & insulin change" (`PumpEventUi.ids`, delete removes both); icons `ic_insulin_pump` (site/insulin/pod changes), `ic_sensor` (sensor changes), `Icons.Filled.Warning` (Announcement, shown as "Warning" with its text in the amber `Warning` colour, `ALARM_PUMP_EXPIRED` prettified). Converted notes have no duration (a temporary 90 % switch from a note counts until the next switch). Not seen on a real phone screen yet.

## Phone connection (Xiaomi 14, `23127PN0CG`, Android 16): classic `adb tcpip` via WireGuard (added 2026-10-06)

The only supported way to reach the phone from this server. It works on **Wi-Fi and mobile data alike**, because adb only talks to the phone's WireGuard tunnel IP; the phone listens on tcp/5555 on every interface. No pairing, no mDNS, no Wireless debugging (which needs Wi-Fi and a new port after every toggle — the old `scripts/adb-connect.sh` port-scan helper was removed). Verified 2026-10-06 with Wi-Fi off, LTE active: `installDebug` ~25 s, app launched, logcat OK.

- Phone tunnel IP: `10.200.200.2` (server `10.200.200.1` on `wg0`; the phone's peer has `AllowedIPs = 10.200.200.2/32`). Connect with `adb connect 10.200.200.2:5555`; `adb devices -l` must show `device`. This server's adb key is already authorized (no prompt expected; if "Allow USB debugging?" appears, tick "Always allow").
- **One-time / after every phone reboot** (TCP mode is reset by a reboot): USB debugging on, phone on USB to the laptop, then in PowerShell
  `adb devices` (accept the RSA prompt; must say `device`), then
  `adb -d tcpip 5555` → expect `restarting in TCP mode port: 5555`. Unplug; don't reboot; keep WireGuard connected.
- Port 5555 must only be reachable through the tunnel: never port-forward it or open it on a public interface. Note `adb tcpip` listens on all phone interfaces (only authorized adb keys can use it) — turn USB debugging off when not developing.
- Commands (export `JAVA_HOME`/`ANDROID_HOME`/`PATH` first, see above):
  ```
  ./gradlew installDebug
  adb shell am start -n uk.scimone.diafit/.MainActivity
  adb logcat -d --pid=$(adb shell pidof uk.scimone.diafit)   # app logs
  adb logcat -b crash -d                                     # crashes
  ```
- **Reconnect:** if `adb devices` doesn't list the phone, run `adb connect 10.200.200.2:5555` again. "Connection refused" ⇒ the phone rebooted (or USB debugging was toggled), so TCP mode is gone: repeat the USB + `adb tcpip 5555` step on the laptop. A timeout ⇒ VPN/routing problem, see below. "offline"/"unauthorized": `adb disconnect`, `adb kill-server`, connect again, re-accept the prompt on the phone.
- **Troubleshooting order:** (1) `ping 10.200.200.2`; (2) `sudo wg show` on the server — the phone peer needs a recent handshake and `allowed ips: 10.200.200.2/32` (needs a real terminal for sudo); (3) the phone's WireGuard tunnel needs `PersistentKeepalive = 25` (carrier NAT drops idle mappings); (4) exempt the WireGuard app from battery optimization and ideally set it as Always-on VPN; (5) `adb kill-server` and reconnect. No firewall (ufw/iptables) rules blocked tcp/5555 on this server as of 2026-10-06 (`ufw` isn't installed).

### Runbook: bringing a pump / pod change in (planned 2026-10-10)

Goal: a pod change appears in the Journal (and is stored with its raw JSON). Nothing is known yet about what AAPS calls it, so first capture, then adapt.
1. **Before:** Settings → bolus source must be **AAPS** (events are ignored otherwise). The phone must be on the app version with DB v16 (`./gradlew installDebug`).
2. **At the change:** in AAPS, change the pod as usual, and make sure the change is logged as a therapy event (**Site Change** and/or **Insulin Change**; AAPS Omnipod Dash normally does this on pod activation; otherwise add it by hand under Careportal). Expect also a priming/activation bolus, which arrives as an ordinary bolus.
3. **After (do it within the day):** read what actually arrived, from the server, no USB needed (phone via WireGuard, see the phone-connection section):
   ```
   export PATH=~/Android/Sdk/platform-tools:$PATH
   adb connect 10.200.200.2:5555
   adb exec-out run-as uk.scimone.diafit cat databases/diafit_database > /tmp/d.db
   adb exec-out run-as uk.scimone.diafit cat databases/diafit_database-wal > /tmp/d.db-wal   # copy the -wal next to it before opening
   sqlite3 /tmp/d.db "select datetime(timestampUtc/1000,'unixepoch','localtime'), eventType, notes, rawJson from PumpEventEntity order by timestampUtc desc limit 20"   # or python3 sqlite3
   ```
   Every non-bolus, non-carb treatment is in `PumpEventEntity.rawJson`, so no logcat is needed (the logcat buffer is only ~2 MiB, i.e. hours; `adb logcat -d -v time AapsEventParser:I` prints each treatment's eventType but may already be gone).
4. **If the change is there but not in the Journal:** its `eventType` doesn't match `PumpEventEntity.isMilestone`'s regex (`core/domain/model/PumpEventEntity.kt`). Add the word, rebuild, install; stored rows show up retroactively (the filter runs at display time).
5. **If nothing arrived:** AAPS didn't broadcast it. Check in AAPS → NSClient/Careportal that the event exists, then whether the `NEW_FOOD` broadcast fired (`adb logcat -d -v time HealthReceiver:D AapsEventParser:I '*:S'` right after logging an event). Fallback: a Nightscout poll for `treatments` with `eventType` Site Change / Insulin Change (not implemented).
6. **Nice follow-ups once real names are known:** a friendlier title/icon per type (pod change vs. sensor change) in `PumpEventCard`/`PumpEventUi`, chart markers on Home/History at the event time, "pod age" on Home (time since the last Site/Insulin Change), and device events in the History day journal.

**Profile switch model (2026-10-07, later):** a switch is always temporary (max 168 h) with up to three kinds of change: percentage, time shift (`timeshift` hours; `AapsProfile.atTimeShift` moves schedules *later*, an assumption about AAPS' sign convention that is not verified against a real shifted switch) and temporary target (not parsed yet; may arrive as its own "Temporary Target" event, to be treated as a switch type once seen). The diff page compares only the time the switch was in force (`DayWindow`, `clipChanges`; >= 24 h shows one day), shades that stretch in the charts, shows the basal insulin impact (`basalInsulin`, excludes temp basals/boluses) and keeps the changed-values list collapsed under each chart. Basal uses the dark-blue `Basal` colour (`ui/theme/Color.kt`, universal for basal), bolus and ISF the lighter `Bolus` blue.

**Temporary target as part of a profile switch (2026-10-07):** AAPS sends a switch and its temporary target as two events ~10 s apart. `pairTemporaryTargets` (AapsProfile.kt, window `TARGET_PAIR_WINDOW_MS` = 2 min) pairs them: the Journal shows one Profile Switch card with a green "Target 150 mg/dL · Activity" chip, the detail page gets a target chip and a "Temporary target" card (profile target → temporary, delta, time range, reason) in place of the target list, and Delete removes both. A Temporary Target with no switch nearby stays its own Journal card (small dialog, no detail page).

**Target-only switches & list card (2026-10-07):** a Temporary Target without a nearby switch is treated as a profile switch that only sets a target: same Journal card and the same detail page (`TargetOnlyContent`: header + target card, the "before" target comes from the profile in force at that time). On switch pages only the cards the switch actually touches are shown (basal / ISF / carb ratio / target when they differ in the window; summary only when something besides the target changed). `PumpEventCard`: time and duration on the first line ("21:05 · 10 min"), title, profile name or target reason, and right-aligned coloured values (target green, percentage `Basal` blue, time shift tertiary); null values are omitted.

### Nightscout data: what we use, what exists, and a possible 2-week backfill (researched 2026-10-08, NOT implemented)

Researched from the code and Nightscout's docs; **nothing here was checked against the user's own Nightscout instance** (that would use the stored URL/API secret from the app's settings; offered, not done).

**What the app takes from Nightscout today:** only CGM readings: `GET /api/v1/entries/sgv.json` via `NightscoutApi.getCgmEntries` (`find[dateString][$gte/$lte]`, `count = 10000000`), mapped to `CgmEntity` by `CgmSyncSourceNightscout`. Each sync resumes from the newest stored reading (or the last hour on a first sync), so **gaps before the newest stored reading are never filled** (e.g. History showed empty days 3-5 Oct 2026 even though Nightscout may have them). Auth is a `?apiKey=` query param (`constructUrl`), but Nightscout expects a SHA-1 hashed `api-secret` header, or a token / JWT bearer; this is open item #3 and **blocks reading private data such as treatments** from a protected instance. Everything else (boluses, carbs, temp basals, profile switches, targets, device events) only arrives live from AAPS by broadcast (`NEW_FOOD` for treatments, the `info.nightscout.androidaps.status` data broadcast for temp basals; see the AAPS sections above).

**What Nightscout has that we don't read:**

| Collection | Contents | Diafit |
|---|---|---|
| `entries` | `sgv`; also `mbg` (finger-stick meter) and `cal` (calibration) records | only `sgv` |
| `treatments` | boluses (incl. SMB), carbs, temp basals, profile switches, temporary targets, site/sensor/insulin changes, notes, exercise | not read; live from AAPS only |
| `devicestatus` | IOB, COB, enacted and suggested loop output, pump reservoir/battery/status, uploader battery (large rows: prediction arrays) | not read |
| `profile` | basal, ISF (`sens`), carb ratio (`carbratio`), targets, DIA, timezone | not read; profile switches come from treatments / broadcasts (AAPS puts the whole profile in `profileJson`) |
| `food` | food database | not read |
| `settings` | server settings | not read |

v1 documented schemas: Entry (`type, dateString, date, sgv, direction, noise, filtered, unfiltered, rssi`), Treatment (`eventType, created_at, glucose, glucoseType, carbs, protein, fat, insulin, units, transmitterId, sensorCode, notes, enteredBy`), Devicestatus (`device, created_at, pump{clock, battery, reservoir, status}, uploader{batteryVoltage, battery}, xdripjs{...}`), Profile (`sens, dia, carbratio, carbs_hr`). v1 endpoints: `/entries`, `/entries/{spec}`, `/treatments`, `/devicestatus/`, `/profile`, `/status`, with `find[field][$op]=value` and `count`; by default /entries and /treatments return only the newest 10 values of the last 2 days unless `count`/date filters are given. I did not find an `activity` or `food` endpoint in the v1 swagger and could not confirm an activity collection.

Nightscout care-portal event types (from `lib/plugins/careportal.js`): Meal Bolus, Snack Bolus, Correction Bolus, Carb Correction, Combo Bolus, BG Check, Announcement, Note, Question, Exercise, Site Change, Sensor Start, Sensor Change, Sensor Stop, Pump Battery Change, Insulin Change, Temp Basal Start, Temp Basal End, Profile Switch, D.A.D. Alert (fields per type: bg, insulin, carbs, protein, fat, prebolus, duration, percent/absolute, profile, sensor...). AAPS-seen on this phone: `Meal Bolus`, `Carb Correction`, `Profile Switch`, `Temporary Target`, `Temp Basal` (AAPS' own names; other AAPS names such as SMB-as-`isSMB:true` boluses, Site/Insulin Change are known from AAPS but the pod-change names are still unverified, see the pod-change runbook).

**API v3** (`/api/v3/...`, self-documented at `/api/v3/swagger-ui-dist/`): collections `devicestatus, entries, food, profile, settings, treatments`; `/api/v3/version` is public, `/status` and `/lastModified` need a JWT (obtained via `/api/v2/authorization/request/{accessToken}`); every document has `srvModified`; **incremental sync** via `/api/v3/lastModified` and `/api/v3/{collection}/history/{lastModified}` (deleted documents arrive with `isValid:false`); search supports `limit`, `sort$desc=date`, `fields=dateString,sgv,direction` and generic filters. Max page size not confirmed (check the instance's Swagger page).

**Possible one-time "Import last 2 weeks from Nightscout" (design notes):**
- A button in Settings starting a background worker (WorkManager), safe to repeat (idempotent). Prerequisite: fix auth (`api-secret` SHA-1 header or token) so private instances work.
- CGM: 14 d is about 4,000 readings at 5-min spacing (about 20,000 at 1-min); would fill the 3-5 Oct gaps. Make the sync resume logic also able to backfill a range instead of only "since newest".
- Treatments: carbs, boluses/SMBs and profile switches map onto what the app already stores; reuse the existing parsers (`AapsCarbParser`, `BolusSyncSourceAaps`, `AapsEventParser`) and dedupe on Nightscout's `_id` (`MealRepository.existsBySourceId`, `PumpEventEntity.sourceId`). **Caveat:** the live broadcast sometimes arrives without `_id` and then the parser keys `"eventType-timestamp"`, so the same treatment can be stored twice across the two channels: also match on time + type.
- Temp basals: Nightscout `Temp Basal` treatments carry exact start, rate/absolute and duration, including cancellations, which is **better than the live status broadcast** (that only shows the loop's latest enact); would feed `PumpEventEntity` ("Temp Basal", `sourceId` shape differs from the `temp-basal-<enactedTimeStamp>` ones, so dedupe by time).
- Device events (site/sensor/insulin changes, notes) would fill the Journal; also provides the real eventType names for pod changes.
- Profile history: `profile` collection or the Profile Switch treatments (`profileJson`) would give basal schedules for time before the first switch the app has seen (today the Basal panel is blank before the first stored Profile Switch, 2026-10-08 12:47 on the dev phone).
- `devicestatus`: skip, or fetch only IOB/COB/reservoir (rows are large because of prediction arrays).
- Open decision: whether to build it, and whether to first query the user's instance (using the URL/key stored in Settings) to see what it actually holds.

### Basal chart styles (2026-10-08)

Settings → "Basal chart" picks a `BasalStyle` (`settings/domain/model`, stored by `SettingsRepositoryImpl` as `basal_style`, applied via `SettingsChangeBus`): **RATE** (the filled step line of the delivered rate, default) or **DEVIATION** (`DeviationCanvas` in `ComponentBasalChart.kt`): bars from a middle zero line for every stretch where delivered != scheduled (up = more than scheduled, down = less), the basal insulin-activity curve over them, and each SMB (`SmbMark`, from `BolusEntity.isSmb`) as a triangle pointing at the bar from outside it (down above positive bars, up below negative ones), size ∝ sqrt(dose) up to 1 U. Home and the History day charts both pass `style`/`smbs` to `BasalDisplay`. **Not verified on-device** (compiles and installs only; the layout was taken from `basal_chart.png`, and the triangle placement rule is my reading of the sketch).

**SMBs (2026-10-08):** SMBs are shown *only* as triangles on the basal panel (Difference style: pointing at the bar; Rate style: under the zero line pointing up, the zero line moves up to make room). The Home basal heading shows the rate plus **basal insulin on board** (`basalRemainingInsulin`, BasalTimeline.kt: remaining area of the basal activity curve, i.e. temp-basal differences + SMBs, can be negative). On the bolus/carb panels every event gets a tick dot, merged or not (drawn *under* the bubble, which the user prefers: drawing it on top looked different). Panel headings align label and value by text baseline (`alignByBaseline`), not by box bottom. They are excluded from the Home/day bolus activity chart and bubbles, from standalone-bolus cards in the Journal and day journal (`standalone()` drops `isSmb`), and from the History overview insulin strip (`DayHistoryUi.insulin`; their units are kept in `smbUnits` so day/period insulin totals and the stats views still include them). Meal outcomes ("insulin for this meal") still count them. `toSmbMarks()` merges SMBs chained within 15 min (a group spans at most 30 min) into one `SmbMark` (summed dose at the dose-weighted mean time; `SmbMarkTest`); triangle size is sqrt(dose) with the maximum at 2 U. The basal-panel activity curve **does** include SMB insulin (`basalInsulinActivity(..., smbs)`). The day Stats tab shows Carbs, Bolus (manual only), Basal (`deliveredUnits`: rate x time of the day's segments, so only up to now and only where a schedule is known) and SMB (only when there are any). Not yet seen on-device with real SMBs, and the new Stats row hasn't been looked at on-device.

### Device status & ages (2026-10-08)

Neither Nightscout nor AAPS reports a sensor / site / cartridge / battery **expiry** (Nightscout's SAGE/CAGE/IAGE/BAGE are ages computed from change treatments; AAPS' status broadcast has none). `DataType.DEVICE` is now labelled **"Device status"** (it was "Pump & sensor changes"; the short-lived separate DEVICE_STATUS type was folded into it): change events come from AAPS or Nightscout as before, and when Nightscout is the selected source `NightscoutSyncWorker` also fetches `/api/v1/devicestatus.json` (`NightscoutApi.getDeviceStatus`); `NightscoutDeviceStatusParser` merges the newest docs (pump reservoir, pump battery % / V, uploader battery %, pump status; each field from the newest doc carrying it) into `DeviceStatusStore` (prefs, one snapshot). Levels also come live from AAPS: `AapsStatusReceiver` parses the status broadcast in place (`AapsDeviceStatusParser`; real extras seen 2026-10-08 on an Omnipod setup: `pumpReservoir` U, `phoneBattery` %, multi-line `pumpStatus` text of which only the first line is shown; **no pump-battery extra for a pod**, `rigBattery` ignored) and merges them into `DeviceStatusStore` when AAPS is the selected source (verified on-device). The receiver logs every extra's name (`adb logcat AapsStatus:I`). **Devices page** (⋮ menu → Devices, `Overlay.Devices`, `devices/presentation/`): per `DeviceKind` the newest matching change event -> age, "due in / overdue by", progress bar, plus a Levels card. Lifetimes are user settings (Settings -> "Device lifetimes", entered as days + hours, stored as hours, `DeviceLifetimeStore`; defaults sensor 14 d, site/insulin 3 d, battery 30 d). `deviceLayout` (shared by the Devices page and the lifetime settings, inputs from `DeviceInputsSource`) decides the rows: a **patch pump** (one "Patch pump (site & insulin)" row, min of both lifetimes; in Settings one field that sets both) is recognised by the `pumpType` AAPS puts on its treatments (`BolusEntity.pumpType` of the latest bolus, e.g. `OMNIPOD_DASH`, also in stored temp basals' raw JSON; regex omnipod/eopatch/eoflow/medtrum), else by every Site Change having an Insulin Change within 2 min and vice versa (60-day look-back); the battery row (page and settings) only exists when a battery level is reported or a battery change was logged. The status broadcast itself carries no pump type. Unit-tested (`DeviceStatusTest`); **not verified on-device against a real Nightscout**, page not looked at on screen.

### Notifications & expiry alerts (2026-10-08)

A bell in the top bar (left of ⋮; red `Badge` while anything is unread) opens `Overlay.Notifications` (`notifications/presentation/`): recent notifications, tap = open the Devices page, everything is marked read when the page is left (`NotificationsViewModel.markAllRead` on dispose). Stored in `AppNotificationEntity` (DB **v18**, `MIGRATION_17_18`, `NotificationDao`; unique `dedupeKey`, entries older than 30 days are pruned). `DeviceExpiryWorker` (periodic 15 min from `DiafitApp.onCreate` + `checkNow()` on app open, `DeviceExpiryScheduler`) runs `deviceAges` and `expiryAlerts` (`AppNotification.kt`, unit-tested): sensor alerts at 24 h and 1 h before expiry, site / insulin / patch / battery at 10 h and 1 h; only the smallest threshold already crossed is raised (a late check says "1 hour", never a stale "10 hours"), nothing once expired; key = kind + change time + threshold, so each alert is raised once per change. A new alert is inserted and, if the insert was new, pushed via `NotificationManagerCompat` (channel `DEVICE_EXPIRY_CHANNEL`, high importance; tap opens the app). `MainActivity` now requests `POST_NOTIFICATIONS` on Android 13+ (it never did before; without it pushes are silently skipped but the bell still fills). Expiry is only as good as the lifetimes in Settings and the logged changes. **Verified on-device:** migration, bell renders; **not yet seen:** an actual alert, the red dot, the push, the list page.

### Glucose patterns (2026-10-08)

`patterns/` ports the backend's AGP pattern detection, specified in `patterns.md` (repo root). `PatternAgp` (domain) is a separate AGP from History's `AgpProfile`: 288 five-minute bins, p10/p25/p50/p75/p90, rounded to 1 decimal; each bin pools ±2 neighbouring bins (widened up to ±6 when sparse; needs 10 readings), numpy-style linear-interpolated percentiles from a per-bin mg/dL histogram, then the same Gaussian smoothing as the chart (`gaussianSmoothCircular`, `AGP_SMOOTHING_MINUTES` = 25, core/domain/model/CircularSmoothing.kt; a deliberate deviation from the backend, chosen by the user 2026-10-08, so a pattern is never raised by a dip the chart doesn't show — on the dev phone it cut 5 patterns to 1), and no profile with < 5 days of data or if any time of day stays too sparse. `detectAgpPatternTexts` follows the spec exactly (order, strict/inclusive comparisons, strings); `PatternDetectionTest` checks the spec's reference vectors A/B/C. `AgpPattern` adds a tone (DANGER / CONCERN / GOOD) and the dashboard's highlight hours (§4 table, plus Somogyi → 02–08, my addition). `GetGlucosePatternsUseCase` uses the last 14 days of CGM.
**Alerts:** `PatternWorker` (every 12 h + on app open, `PatternScheduler`; runs serialised by a mutex since both start together) notifies about non-GOOD patterns that weren't found on the previous check and weren't alerted in the last 7 days (`newPatternAlerts`, state in `PatternAlertStore` prefs), batched into one notification. Notifications now carry a `link` (DB **v19**, `MIGRATION_18_19`; `notifications/domain/NotificationLinks.kt`: `devices` or `patterns:` + pattern texts joined by `|`; null = Devices for older rows). `AppNotifier` (notifications/data) stores + pushes for both workers; the push intent carries `AppNotifier.EXTRA_LINK`, read by `MainActivity` in `onCreate`/`onNewIntent` (`pendingLink`). Tapping a notification in the bell list routes the same way. **Removing** (2026-10-08): swipe either way or the ✕ on a card, Undo snackbar; it's a soft delete (`AppNotificationEntity.isDeleted`, DB **v20**, `MIGRATION_19_20`) because the row's unique `dedupeKey` is what stops the expiry worker re-raising the same alert; `AppNotifier.cancel(key)` also clears the push. Not yet tried on-device (compiles, migration ran).
**Page:** `Overlay.Patterns(highlighted)` (also ⋮ menu → Patterns): the pattern AGP via History's `AgpPlot` (now generic: `AgpBands`, any bin count, Gaussian smoothing `AgpBands.smoothed` + curved paths (quadratic segments through midpoints); Patterns passes `smooth = false` since `PatternAgp` is already smoothed, `highlights` washed + rest dimmed, overlapping spans merged, optional y labels), patterns split into "Needs attention"/"Going well", tap to toggle highlighting. Verified on-device with real data (5 patterns over 14 days, page opened through the notification link). Test via `adb shell am start -n uk.scimone.diafit/.MainActivity -f 0x24000000 --es uk.scimone.diafit.NOTIFICATION_LINK "'patterns:Dawn phenomenon detected'"`. Not yet seen: the actual push on the phone's shade, a pattern disappearing and reappearing.

### Backend sync (optional module, 2026-10-08)

`backendsync/` uploads local data to the user's own Diafit backend (API spec: `diafit_backend_api.json`, v2, `Authorization: Bearer <token>`). Self-contained so it can be hidden or removed: `BackendSyncFeature.ENABLED` guards the only hook points (`DiafitApp` Koin module + `BackendSyncScheduler.schedulePeriodic()`, `MainActivity` `syncNow()` on open, the Settings "Backend sync" section, `AppDatabase.backendSyncDao()` = read-only queries, no tables/migration). To remove: delete the package and those lines.
- Settings: address + API token, "Save & test" checks `GET /api/v2/me` and only saves a working config; then summary line (Test/Edit), last sync + result, Sync now, Disconnect. Stored in plain prefs (`BackendSyncStore`, files `backend_sync`, `backend_sync_meals`); changing address/token resets all upload progress.
- `BackendSyncWorker` every 15 min (network constraint, exponential backoff; retries only on unreachable/5xx, a 401/422 waits for the next run). `BackendSyncer`: CGM, boluses, heart rate are paged by local row `id` (cursor per type, 2000 rows per `POST /<resource>/bulk`; tables are insert-only, a REPLACE gives a new id so re-imports are re-sent and the idempotent bulk endpoints skip them); sleep sessions = sessions with stage rows newer than the cursor; meals: new in bulk, edited/deleted (soft delete -> `is_valid:false`, merged AAPS rows also `is_valid:false`) found via `GET /meals` around the last uploaded time by `source_id` and `PATCH`ed (state = content hash + time per meal). App meals get `source_id = diafit-meal-<createdAtUtc>-<id>`. Steps (`POST /steps/bulk`, one entry per 15-min slot, `source_id = hc-steps-<startUtc>`): Health Connect keeps rewriting recent slots and bulk never updates, so a slot is uploaded only once it is 3 h old (`STEPS_SETTLE_MS`; time cursor `steps_through`) plus any older slot written since the last upload (id cursor, backfills); a correction after that is not sent. Mapping in `backendsync/domain/BackendPayloads.kt` (`BackendPayloadsTest`). The module has its own Ktor client (no body logging, Authorization sanitized). Workouts, pump events/temp basals have no backend endpoint and are not uploaded; nothing is downloaded. First sync uploads the whole history.
- **Verified:** unit tests, install, Settings section renders. **Not verified against a real backend** (unknown: the server's duplicate identity rules, whether `GET /meals` returns `source_id` as expected).
